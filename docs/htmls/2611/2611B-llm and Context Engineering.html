01. FUNDAMENTAL ARCHITECTURE

1. 生成AIの基本構造：ステートレス関数としてのLLM

02 / 09
Core Mathematical Model（基本動作式）
次のトークン（文字の断片） ＝ LLM(コンテキスト)
LLMは会話の記憶を持たない
「純粋な次単語予測マシン」である
よくある誤解（ステートフルな人間モデル）

「AIが過去の会話を覚えている」

AIの内部にセッションごとの記憶領域があり、2ターン目以降は「さっきの続き」だけを差分として送っているとイメージしがちです。

Turn 1: User「申請方法は？」 → AI（内部に記憶）
Turn 2: User「期限はいつ？」 → AI（記憶から回答？）
※ 実際にはLLM単体に状態（State）は一切残らない
実際の動作（ステートレス再入力モデル）

「毎回、全履歴を束ねて丸ごと再入力している」

チャットアプリ（システム）側が、過去のやり取り・システム指示・参照資料を1本のテキスト（コンテキスト）に連結し、毎ターン最初からLLMへ渡し直しています。

Turn 1: LLM([指示 + Q1]) → A1
Turn 2: LLM([指示 + Q1 + A1 + Q2]) → A2
→ 1トークン生成するたびに文脈全体から続きを予測
02. MENTAL MODEL

脳（LLM）と作業机（コンテキスト）の役割分担

03 / 09
コンテキスト（作業机の上の1本の長いテキスト） 短期記憶・作業スペース
[1]
システムプロンプト（AIの役割・前提ルール）
例：「あなたは親切なITエンジニアです。簡潔に回答してください。」
[2]
外部知識・参照データ（RAG等で検索して貼った資料）
例：「社内マニュアル：有給休暇は前日までにポータルから申請…」
[3]
会話履歴（これまでのユーザーとAIの全発言）
User: 申請方法を教えて ／ AI: 社内ポータルから申請できます。
[4]
今回のユーザー入力（最新の質問・指示）
User: 期限はいつまで？
※ [1]〜[4] が上から順に連結され、丸ごとLLMへ入力される
LLM（脳・推論エンジン） 事前学習済み

事前学習で獲得した「言語の法則や一般知識」を使い、作業机に置かれたテキストの「最も自然な続き」を1トークンずつ予測します。

INPUT: [1] + [2] + [3] + [4] を一括読込
PROCESS: 確率分布から次トークンを計算
OUTPUT（1トークンずつ生成）
AI : 前日までに申請してください。
設計の本質

LLM（脳）の知識は固定されているため、実務では「限られた作業机（コンテキスト）に何をどう並べるか」が品質のすべてを決めます。

03. DERIVED PHENOMENA

基本構造から説明できる3つの現象

04 / 09

「ステートレスなLLM × 有限の作業机（コンテキスト）」というシンプルモデルを押さえると、実務で遭遇するAIの弱点や挙動がすべて論理的に説明できます。

生成AIの挙動・現象 シンプルモデルでの仕組み上の理由 実務上の対策アプローチ
Context Overflow
会話が長くなると
最初の指示を忘れる
コンテキストには「コンテキストウィンドウ」と呼ばれる容量上限（トークン数の枠）があります。会話が積み重なり枠から溢れると、古い情報から切り捨てられ（押し出され）、LLMの視界から完全に消えるためです。
対策
不要な履歴の要約・リセット、重要ルールのシステムプロンプト固定
Hallucination
最新情報や社内データについて
嘘をつく（ハルシネーション）
LLM本体の知識は事前学習時点で固定されています。コンテキストの [2] 参照データ 領域に資料を貼らない限り、LLMは「もっともらしい続きの言葉」を確率的推測で穴埋めしてしまいます。
対策
RAGによる根拠資料の注入、「資料にないことは答えない」制限の明記
Lost-in-the-Middle
長文の真ん中にある
情報を見落とす
コンテキストが長大になると、モデルの注意機構（Self-Attention）が分散します。結果として、文章の最初（先頭）と最後（末尾）に比べて中間の情報の重みが薄れやすくなります。
対策
情報の厳選・構造化、最重要指示の先頭または末尾への配置
04. MODEL SCALE & PARAMETERS

2. LLMの規模：「パラメータ数」とは？

05 / 09
パラメータ数 ＝ 脳の規模・知識量（ニューラルネットワーク内の「重み」の総数）
事前学習で獲得した言語パターンや知識はすべてこの数値として格納。単位は B（Billion＝10億） / T（Trillion＝1兆） で表記。
小規模モデル 〜 10B 前後
〜 約100億パラメータ

スマートフォンやPC単体（ローカル環境）でも動作する軽量モデル。定型処理・分類・簡単な要約に向き、応答が極めて高速かつ低コストです。

用途：エッジ処理、高速ルーティング、定型抽出
中規模モデル 30B 〜 100B
300億 〜 1,000億パラメータ

一般的なビジネス業務、文書作成、プログラミング支援で高い実用性を持つコストと知能のバランス型です。

用途：業務アシスタント、コード生成、RAG応答
大規模・フロンティア 数百B 〜 1T超
数千億 〜 1兆パラメータ超（※商用最上位は非公開多数）

複雑な多段階論理推論、高度な専門知識、曖昧な指示からの意図汲み取りをこなす最上位クラスです。

用途：複雑設計、高度分析、自律型エージェント
TREND: MoE (Mixture of Experts)

近年は全パラメータを毎回計算するのではなく、入力内容に応じて必要な一部の専門家ネットワーク（Expert）だけを動かすMoE構造が主流。「総パラメータ数は巨大だが、実際に動く（アクティブな）パラメータは一部だけ」という高効率化が進んでいます。

上限128Kのモデルに125K分の資料を入れると、AIが回答を出力する空きスペースは残り3K分しかありません。

注意点②：「入る」ことと「正確に処理できる」は別

上限ギリギリまで詰め込むと遅延・コスト増に加え、中盤の検索精度が低下します。必要な情報だけを厳選する設計が不可欠です。

06. CONTEXT ENGINEERING ARCHITECTURE

3. 意図通りのArtifactを生む「コンテキスト設計」

07 / 09

作業机（コンテキスト）の上に「指示書（ルール）」「教科書（Framework）」「手順書（SKILL）」の3層パッケージを構造化して並べることで、AIの勝手な推測を排除します。

【1】 コンテキスト本体の指示（タスクの設計図・ガードレール） Policy & Guardrails
目的 / 形式・スタイル
ゴールと出力見た目の定義
業務・タスクルール / 制限
判断基準と厳格な禁止事項
成果の検証内容
出力前のセルフチェック基準
【2】 references/（参照すべき知識・型：Framework） Static Knowledge

構成テンプレート、評価軸、過去の成功事例、専門フレームワークを明示的に配置。
→「何をもとに、どんな骨組みで書くか」の根拠（Knowledge）を提供

【3】 skills/（特定タスクの実行手順・ノウハウ：SKILL） Dynamic Procedure

作業ステップ、ツールの使い方、特有の変換ルール、計算ロジックをパッケージ化。
→「どうやって作業を進めるか」の専門手順書（Procedure）を提供

【1】＋【2】＋【3】を一括入力
LLM 推論エンジン
設計図・型・手順を統合処理
HIGH-PRECISION OUTPUT
ユーザー意図に沿った
Artifact（成果物）
誰が実行しても同じ高品質・一貫性を再現
07. ENTROPY REDUCTION MECHANISM

3つの要素が「ブレ」を封じ込めるメカニズム

08 / 09

AIの出力が意図から外れる最大の原因はコンテキスト内の「情報の曖昧さ」です。空白があると、LLMは確率的に「世の中でよくある無難なパターン」で穴埋めしてしまいます。

1. What / Why の固定

ルールと検証による
ガードレール

対象：コンテキスト本体の指示領域

  • 目的・スタイル：着地点を固定し、一般的なブログ風文章への逃避を防止。
  • タスク制限：「やってはいけないこと」が余計な推測を止める強力なブレーキに。
  • 検証基準：出力前の自己点検により制約漏れや形式崩れを激減。
効果：ゴールのブレと脱線を封じる
2. Structure / Basis の固定

Framework による
思考の骨組み固定

対象：references/ ディレクトリ

  • 構成テンプレート：ゼロから構成を考えさせず、毎回同じ論理構造を維持。
  • 評価軸・基準表：判断の拠り所（Basis）を明示し、品質のばらつきを解消。
  • 穴埋めタスク化：「用意された枠組みに今回のデータを当てはめる」確実な作業へ変換。
効果：構成の揺らぎと根拠不足を封じる
3. How の固定

SKILL による
実行手順・技能の固定

対象：skills/ ディレクトリ

  • 動的プロセス定義：「抽出→分類→変換→出力」の思考ステップを順序立てて固定。
  • 専門職への特化：汎用LLMを一時的に「その業務専用の熟練職人」へ変貌させる。
  • 部品化と効率性：必要な技能だけを呼び出し、トークン消費を最適化。
効果：処理手順の自己流アレンジを封じる
08. CONCLUSION & TAKEAWAY 09 / 09

まとめ：コンテキスト・エンジニアリングの本質

LLMが勝手な解釈を挟む隙間を構造的に塞ぎ、
必要な知識と技能だけを過不足なく作業机に並べることで、
誰が実行しても意図に忠実なArtifactを安定生成できる。

生成AI活用の鍵は、LLMの頭脳を魔法のように扱うことではなく、ステートレスな推論マシンに対して「完璧な業務パッケージ」を渡すエンジニアリングにあります。

KEY POINT 01
LLMは予測装置と割り切る

記憶も空気を読む力もない純粋関数である前提に立ち、必要な文脈はすべて明示的にコンテキストへ載せる。

KEY POINT 02
作業机の広さと精度を意識する

入出力の合計トークン枠と中盤の見落とし（Lost-in-the-Middle）を踏まえ、情報を構造化して厳選する。

KEY POINT 03
ルール × Framework × SKILL

境界線（ルール）・型（references/）・手順（skills/）の3層分離で、属人性のない高品質な出力を標準化する。
