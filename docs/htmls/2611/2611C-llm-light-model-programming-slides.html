重いモデルと軽いモデル

重いモデル

  • パラメータ数が非常に大きい（兆規模も）
  • コンテキストも長い
  • 長距離の一貫性・稀な組み合わせに強い
  • 自己批判・自己修正の質が高い
  • コスト・レイテンシが大きい

軽いモデル

  • パラメータ数が小さい／中間
  • 局所的なパターンには強い
  • 長文一貫性や深い検証は弱め
  • 速い・安い
  • プロンプト設計の影響が大きい

言語モデルは学習データから作られた言語空間（多様体）上で次トークンを予測する。
重いモデルはその「面」の解像度が高く、軽いモデルは粗い、というイメージが近い。

プログラミングは「中間モデル」でも戦える

プログラミングの多くは、論理が閉じた狭い領域に落ちる。

  • 文法・型・よくある設計パターンは学習データに大量にある
  • 仕様が明確なら「探索・検索」で正しい実装に到達しやすい
  • アーキテクチャやクラス構造が固定されていると、自由度が下がり精度が上がる
ポイント
「正しいコードを書ける」ことと、
「そのコードが本当に正しい理由まで深く検証している」ことは別物。
軽いモデルは前者に強く、後者は弱い。

したがって、仕様・制約・受け入れ条件を人間が先に固めるほど、軽いモデルの成功率は上がる。

Deep Thinking とは何か

単なる「ステップバイステップで書いて」ではない。

Deep Thinking（深い思考）
  1. 複数の計画・仮説を立てる
  2. それぞれを批判的に評価する
  3. 矛盾がないかを確認する
  4. 必要なら仮説を捨て、別の道を探す
  5. 最終的な答えに至るまで自己修正を続ける

モデル側では、最終回答の前に長い思考過程（Chain-of-Thought）を生成し、
正しさ（検証可能な結果）を報酬に思考の質そのものを学習している、という仕組みが多い。

速い思考と深い思考

観点 速い思考（軽いモデル寄り） 深い思考（Deep Thinking）
動作 パターンマッチで即座に出力 複数仮説を探索してから出力
検証 表面的・局所的 矛盾検出・軌道修正が強い
計算量 ほぼ固定・短い 問題の難しさに応じて長く考える
得意 定型実装、CRUD、変換処理 曖昧要件、複合制約、設計判断
苦手 エッジケースの網羅、長期影響 コスト・待ち時間

軽いモデルに CoT を強制しても、検証そのものの質の上限はモデル能力に依存する。

RLHF と Deep Thinking の違い（要点）

従来の RLHF

  • 目的：人間の好みに沿う回答
  • 報酬：好み・安全性・指示追従
  • 最適化対象：最終出力の好ましさ

Deep Thinking 系

  • 目的：正しい答えに至る思考
  • 報酬：正しさ（数学・テスト通過など）
  • 最適化対象：思考過程の質と戦略

つまり Deep Thinking は「深いフィードバックをたくさん与えた RLHF」というより、
思考そのものを、正しさを軸に強化学習した能力に近い。

軽いモデルの弱点：検証が弱い

プログラミングで軽いモデルを使うとき、次が起きやすい。

  • 正常系は通るが、異常系・境界値が抜けている
  • 「正しそうなコード」を出す（コンパイルは通るが業務的にズレる）
  • 仕様の曖昧さを補完してしまい、意図と違う前提が混入する
  • 複数制約の同時最適化が粗い
重要 深いモデルが内部でやっている「仮説の批判的検証」を、
軽いモデルでは人間が仕様と指示で肩代わりする必要がある。

エッジケースとは何か

エッジケース＝正常系の外側、しかし現実に起こりうる入力・状態・順序。
「まれ」でも、本番では必ず踏まれる。

考える軸（4つ）

  1. 境界値 … 0, 1, 最大, 最大+1, 空, null
  2. 異常系 … 存在しないID、権限なし、形式不正
  3. 同時性・順序 … 二重送信、古いデータでの更新
  4. 関連データの不整合 … 親削除済み、論理削除の混入
仕様が「正常系中心」だと、軽いモデルは正常系だけをきれいに実装する。
エッジケースは仕様に書くか、指示で明示する必要がある。

軽いモデルへの指示：4点セット

深い検証の代わりに、次の4つを毎回明示する。

1. Context（背景・制約）

  • 技術スタック・配置場所
  • 既存の層・禁止事項
  • 優先順位（正しさ＞速度 等）

2. Assumption（前提）

  • 入力範囲・nullの扱い
  • 外部依存の挙動
  • エッジケース方針

3. Goal（達成内容）

  • 何を実現するか
  • 成功の定義

4. Outcome（成果物）

  • コード形式・テスト有無
  • 受け入れ条件の箇条書き

指示例：バリデーション実装

Context:
- Application Service の createOrder に実装
- フレームワークのバリデーション機構を使う
- 外部ライブラリ追加禁止

Assumption:
- customerName: 必須、1〜100文字、前後空白は trim する
- amount: 必須、整数、1〜999999。0 と負数はエラー
- null と空文字はどちらも必須エラー（メッセージは共通でよい）

Goal:
- 注文作成の入力検証を仕様どおりに行う

Outcome:
- 検証関数とユニットテスト
- 正常系1件、異常系（空文字・null・0・上限+1）をテストに含める
- エラーメッセージは日本語で固定文言

境界と異常系を数値・文言レベルで書くことが要点。

12 / 15

指示例：更新と重複チェック

Context:
- UserRepository の updateName(userId, name) を実装
- DB には unique(name) 制約あり

Assumption:
- name は trim 後 1〜50文字
- 重複チェック時は「自分の userId は除外」する
- 大文字小文字は区別する（仕様どおり）
- 存在しない userId は NotFound を返す

Goal:
- ユーザー名を安全に更新する

Outcome:
- 実装コード + テスト
- ケース: 正常更新 / 他人と重複 / 自分と同じ名前 / 存在しないID
- 例外型とメッセージを明記
「自分を除外する」ような暗黙知は、軽いモデルは自力で補完しにくい。
仕様に1行書くだけで失敗率が大きく下がる。

実装前に揃える設計成果物

コーディングを狭い論理空間に落とすための最小セット。

  • ユースケース（基本・例外フロー）
  • 業務ルール一覧（ID付き）
  • IPO（Input / Process / Output）
  • CRUDマトリクス（更新責任の明確化）
  • 入力項目とバリデーション詳細（境界値・異常系付き）
  • 状態遷移（ステータスがある場合）
  • 正常系＋代表的な異常系の入出力例
アーキテクチャとDB設計を人間が固定し、
業務仕様（入力・検証・リポジトリ契約）を渡せば、
中間〜軽いモデルでも実装品質は実用レベルに近づく。

まとめ：実務チェックリスト

  1. 設計判断・曖昧要件は深いモデル（または人間）で固める
  2. 実装は仕様を狭くして軽い／中間モデルに渡す
  3. 毎回 Context / Assumption / Goal / Outcome を書く
  4. 境界値・null・自分自身・不正遷移を仕様に明記する
  5. 受け入れ条件に異常系テストを含める
  6. 「正しそう」で終わらせず、異常系レビューを人間が残す

Deep Thinking の代替は、モデルに丸投げすることではない。
仮説検証のうち「仕様化できる部分」を人間が先に行い、
残った狭い実装空間をモデルに任せることである。
