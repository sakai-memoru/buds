1. 入力と出力の性質

4. 運用継続性
  • 手順がプロンプト consumable になっていないか
  • SKILL化して資産にできるか
  • 他サービスへの移植性

RPAと生成AIの方向性の違い

観点 RPA 生成AI（SKILL + ツール実行）
前提 完全定型ジョブ 非定型・半定型を含む
入力 固定位置・固定形式 自然言語・非構造テキスト可
手順記述 厳密なスクリプト 自然言語 + 必要時にツール呼出
例外 事前分岐を書き切る モデル判断 + 人が最終確認

実践的な最適解はハイブリッド。
例：生成AIが非定型文から JSON/CSV を生成 → PowerShell → Excel VBA で定型操作を実行。

SKILLとは何か

SKILLは、AIへの「保存された手順書」です。その場限りのプロンプトと違い、再利用・共有・横展開できます。

プロンプト
  • その瞬間の指示
  • 会話が終わると消える
  • 口頭のお願い
SKILL
  • ファイルとして残る指示
  • 必要なときだけ読み込まれる
  • マニュアル（資産）

Progressive Disclosure（段階的開示）

1. name + description（常時） → 2. SKILL.md 本文（発動時） → 3. references / scripts（必要時）

コンテキストを圧迫せず、スキルを多数持てる設計思想。

7 / 15

SKILL.md の構造と記述ルール（要点）

必須構造
  • --- で囲んだ frontmatter
  • name（ディレクトリ名と一致）
  • description（トリガーの唯一の入口）
  • 空でない本文（命令形）
description の厳しいルール
  • 1行・引用符なし
  • 最大 1024 文字
  • : （コロン+スペース）禁止
  • < > 禁止
  • 「何を・いつ」を具体語で書く

書いてはいけないこと

  • モデルが既に知っている一般知識の重複
  • トリガー情報を本文だけに書くこと
  • 500行超の肥大化（references に逃がす）

自分でSKILLを書く手順

1. 具体作業を1つ選ぶ → 2. 手作業手順をメモ → 3. 知らない知識だけ抽出 → 4. 最小SKILL.md → 5. 検証・実戦・改修
作る判断
  • 組織・個人特有の手順 → 作る
  • 毎回同じコードを書く → scripts/
  • 一般知識だけ → 作らない
初期の書き方
  • description に発火フレーズを入れる
  • 本文は命令形・簡潔
  • 長い詳細は references/
  • validate スクリプトで構造確認

メタスキル（整理用SKILL）は、実作業SKILLが5〜10個育ってからで十分。

運用時のチェックポイント

観点 確認内容 アクション
利用実績 直近で実際に発動したか 未使用は削除候補
トリガー description だけで発動条件が分かるか 曖昧なら書き直し
重複 似た目的のSKILLが複数ないか マージ
肥大化 本文が長すぎないか references 分割
正確性 古い手順・危険操作が残っていないか 改訂 or 廃止
移植性 他サービスでも使える書き方か 標準形式を維持

目安：10個超えたタイミング、または月1回の棚卸し。

まとめと次の一手

押さえる原則
  • サービスは「接続先」と「実行境界」で選ぶ
  • プロンプトを消費せず、SKILLを資産にする
  • 非定型理解は生成AI、確実実行はスクリプト/RPA
  • 小さく作って実戦で直す
今週やると良いこと
  • 繰り返し作業を1つ選び最小SKILL化
  • description と検証を通す
  • 既存Awesomeから近いSKILLを1つ導入
  • 作業ログの型（背景・対応・結果・学び）を決める

完璧な体系は後から見えてくる。まず「1作業・1 SKILL・1回の実戦」から始めるのが最短距離。
